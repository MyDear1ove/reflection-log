# 维护：晋升、退役、合并

日志会腐烂。三种腐烂方式各有对应的动作：**晋升**（该出现的没出现）、**退役**（不该留的一直留）、**合并**（同一件事散成好几条）。

维护只在三种时刻发生，不设闹钟：

- 要加第 8 条常驻规则时（强制选一条退役）
- 冒出"这条好像跟以前那条重复"的直觉时
- 用户主动说"复盘一下"时

## 一、晋升

`失效 ≥ 2`，或造成**不可逆损失**（删了文件、发了错版本、让用户据此做了决定）→ 立即晋升。

两步：

1. 在 `~/.dsh/AGENTS.md` 的 `reflection-rules` 块里加一行：

```
- R-0007 报告完成前先跑 build 并贴输出；没跑过就说"未验证"。
```

2. 回答里明说一句：`R-0007 已第 2 次失效，提为常驻。`

**一行式的写法**：去掉背景、去掉原因，只留"什么情况 → 做什么"。常驻块每一行都是每个会话的成本，只放动词和条件。

块不存在时，先用 `templates/AGENTS.snippet.md` 建出整块（含 begin/end 标记），再往里写。裸写规则会导致下次找不到块、重复建块。

### 为什么上限是 7 条

常驻块进入每次会话上下文。超过 7 条后，模型对每一条的遵守率都会下降——清单越长执行率越低，机场和手术室的经验一致。第 8 条进来，必须有一条出去。

### 已晋升的规则又失效了怎么办

- 失效 = 3：先怀疑规则本身。它大概率太宽或不可执行，**重写它**（更窄、更具体的动作），`失效` 归零，而不是再加一条更严厉的。
- 失效 ≥ 4：说明重写过一次还是没用。这条规则在你的实际工作里没有落点，退役，并在正文写清为什么——这本身是一条关于"什么样的规则没用"的证据。
- 无论重写还是合并，**回头同步常驻块里的那一行**。常驻块是规则的第三份副本，不写同步就会漂移，最后块里留着一条日志上已经不存在的规则。

## 二、退役

判据必须可数，否则永远不会执行。满足任一即退役：

| 条件 | 判据 |
|---|---|
| 长期未失效 | `日期` 距今超过 180 天，且期间没有再出现同源错误 |
| 已被覆盖 | 新规则更具体地管住了同一件事 |
| 已被合并 | 正文里已有 `- 合并至：R-00xx` |

（不要用"已经内化了"当判据——无法观测，只会变成不退出的借口。）

动作：`状态：active` → `状态：retired`，从顶部索引移到文件末尾的 `## 归档索引`；**若它在常驻块里，把那一行删掉**。正文**保留**。半年后你会想知道自己在同一个地方摔过几次。

退役后同源错误再次出现，说明退早了：恢复 `active`，`失效` 归零，正文加 `- 复活：YYYY-MM-DD <为什么退早了>`，索引移回顶部，需要的话重新写回常驻块。归零是为了不让它刚复活就撞上"失效 ≥ 4 退役"这条线。

从常驻块退出的优先级：失效次数最少 → 最近一次失效最久 → 已被覆盖。

## 三、合并

同一类错误往往产生 3–4 条高度相似的规则。判断标准很硬：**两条规则的"校验"栏几乎一样，就是同一条。**

1. 选**最具体、最可判定**的那条当主条目。
2. 其他条目 `状态` 改 `retired`，正文加 `- 合并至：R-00xx`。
3. 主条目的 `触发` 栏吸收其他条目的触发词（检索靠这个），但总数不超过 6 个。
4. 主条目的 `失效` 取合并前的**最大值**，不求和——求和会把一条早就该重写的规则直接顶到常驻。

## 四、索引膨胀

索引读取预算 **40 行**，所以顶部索引只能放 ≤ 40 条 `active`：

| 规模 | 动作 |
|---|---|
| active ≤ 40 | 照常 |
| active > 40 | 先合并同源（看 `校验` 栏），再退役最弱的；直到 ≤ 40。归档本身不减 active 数，别指望把 retired 挪走就够 |
| 全文件 > 200 条 | 按年份拆文件（`reflections-2026.md`），`reflections.md` 只留当年 |

挑谁退役，按这个顺序看：`失效` 最低 → 最近一次失效最久（要翻正文的 `日期` 和 `复发` 行）→ 已被覆盖。

归档索引行也保留触发词——退役不等于无用，半年后同类问题再出现时，你要能搜索到它。

## 五、冲突处理

新旧规则结论相反时（"上次说要先问，这次说要先做"），不要两条都留。先分辨是哪一种：

1. **情境不同** → 不是冲突，把两条的 `触发` 栏各自写精确。
2. **旧规则错了** → 旧条目标 `retired`，正文加 `- 被 R-00xx 推翻：<一句原因>`。
3. **真的两难** → 合成一条带条件的规则：「情况 A 做 X，情况 B 做 Y」，并把 A/B 的判据写进 `校验`。

第 3 种最有价值——它通常说明你发现了一个真实的权衡，而不只是记错了一次。

## 六、当用户嫌这套东西烦

这一定会发生。用户说"别每次都写这行"时，不要辩解，也不要照做后就地关掉机制。正确做法是记一条 `偏好` 类规则：

```
### R-0021 · 约束行在小任务上变成噪音
- 日期：2026-12-02
- 标签：沟通/偏好
- 触发：简单问题｜一句话｜确认一下
- 事件：用户问一个单句问题，我回了"按 R-0007：……"，用户说"别每次都写这行"。
- 规则：任务不涉及交付物时，不写"按 R-xxxx"约束行，只在内部自查。
- 校验：纯问答里出现"按 R-"开头 → 违规
- 失效：0
- 状态：active
```

用规则去缩小触发范围，而不是让用户来关开关——关掉之后就再也不会恢复了。
