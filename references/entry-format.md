# 条目格式

## 一条记录的完整结构（八字段）

```
### R-0007 · 未验证就宣称完成
- 日期：2026-11-13
- 标签：交付/测试
- 触发：做完｜完成报告｜结果
- 事件：命令超时，我说"已修复"；用户重跑仍然报错。
- 规则：报告完成前必须贴出实际执行的命令与关键输出；没跑过就说"未验证"。
- 校验：回答里出现"已完成/已修复/应该可以"但无命令输出 → 违规
- 失效：0
- 状态：active
```

- ID 单调递增，取索引里最大 ID + 1，不复用、不跳号。
- `日期` 固定 `YYYY-MM-DD`，退役判据靠它算 180 天，别写"11月13日"。
- `失效`：该规则**被违反**的次数。不统计被检索到的次数。
- `状态`：只有 `active` / `retired`。`retired` 保留正文，不删。
- 标题行固定 `### R-0007 · 一句话`，这样才能用 `grep '^### R-'` 数条目数。
- 同一条规则再次被违反时，不加新条目，在正文末尾追加 `- 复发：YYYY-MM-DD <情形>`，`失效` 加 1。

注意：正文里的分隔符写 `交付/测试`，不加空格；`触发` 内用全角 `｜` 分隔。格式必须和索引行一致，否则检索会漏。

## 索引行（五字段）

写在文件顶部索引区，一行一条，字段顺序固定，用 ` | ` 分隔：

```
R-0007 | 交付/测试 | 未验证就宣称完成 | 做完｜完成报告｜结果 | 失效=1
```

`ID | 标签 | 标题 | 触发词 | 失效次数`

索引里**必须有触发词**——只靠标签和标题判断相关性，会漏掉措辞不同的同源情况。索引行不写 `状态`：顶部索引里的全是 `active`，`retired` 的移到文件末尾的 `## 归档索引`。

索引行**不得再包含半角 `|`**（触发词里也不许用），否则字段会错位。分隔用全角 `｜`。

索引与正文不一致时（改了正文忘了改索引，或反之），**以正文为准**，按正文重建那一行。

## 六个实质字段各自的判定标准

### 事件：只写事实

- ✅「命令超时，我说已修复，用户重跑仍报错」
- ❌「这次表现不好，没有足够谨慎」
- 判据：换成另一个人来看，他能确认这件事发生过。

### 规则：可执行动作

规则是**这次要改变的行为**，不是态度。

| 不合格 | 为什么 | 改成 |
|---|---|---|
| 要更仔细地检查代码 | 无法判定 | 改完代码先跑一次 `build`，通过再回复 |
| 注意用户偏好 | 太抽象 | 用户说"短一点"之后，同一话题正文不超过 5 行 |
| 不要犯同样的错 | 没有内容 | （这句本身就不含规则） |
| 提高回答质量 | 不可判定 | 给结论前先写一个反例自检 |

粒度：**太窄**只对一次有效（"这次的 CSV 要 UTF-8"）；**太宽**无法判定（"要保证正确"）。合适粒度是"一类任务"——"凡是导出文件，先确认目标编码"。

规则里不要写"应该""尽量"。写"必须"或"不做"。

### 触发：未来屏幕上真会出现的词

检索能否匹配到的唯一依据。写的时候问自己：**下次遇到这事，屏幕上会出现哪些字？**

- ✅ 用户会说：「做完」「好了吗」「可以了」
- ✅ 任务名会含：「导出」「周报」「审阅」
- ❌ 抽象动机：「涉及到质量的时候」「需要谨慎时」——屏幕上不会出现这些字
- 3–5 个词，用 `｜` 分隔；至少一个来自**用户原话**，至少一个来自**任务类型名**。
- **写词干，不写整句**：用户说「做完了吗」，触发词写「做完」。中文没有空格切词，整句几乎匹配不到别的说法（「做完没」「做完了没」都对不上）。
- 触发词不是越多越好：超过 6 个会开始匹配到无关任务，让规则变成噪音。

### 标签：从固定词表里选

`交付` `测试` `写作` `研究` `沟通` `工具` `时间` `风险` `偏好`

一条最多两个，主标签在前。要区分项目专属的教训，把项目名挂在第二层：

`交付/Inspiration`

不要每次造新词——词表膨胀后检索就退化成猜。

### 校验：可观测的违规信号

写成"如果我看到 X，就是违反了"，能让别人对照回答直接判断。

- ✅「回答里出现'已完成'但没有任何命令输出」
- ✅「正文超过 5 行，且用户上一轮说过要短」
- ❌「感觉不够严谨」

校验栏还有一个用途：**任务结束时拿它自查一次**。这是防"仪式性合规"的唯一手段——写了约束行不等于遵守了。

### 失效：只加 1

- 每次违反 +1，不批量改。`失效` 只影响晋升与重写，不影响检索。
- 加 1 的同时必须有对应的 `复发` 行，否则这个数字没有依据。

## 三个完整示例

### 例 1｜沟通类

```
### R-0012 · 给了三个方案却没给推荐
- 日期：2026-11-15
- 标签：沟通/写作
- 触发：几个方案｜你觉得呢｜选哪个｜建议
- 事件：用户问怎么做，我列了 A/B/C 三种做法和优缺点，没有说选哪个；用户回"那你觉得呢"。
- 规则：给方案的同一段里必须有一个明确推荐并附一句理由；确实不该选时，说明缺哪个信息。
- 校验：出现并列方案但整段无"我建议/我选" → 违规
- 失效：1
- 状态：active
- 复发：2026-11-18 又一次并列三个方案，仍然没给推荐。
```

### 例 2｜研究类

```
### R-0018 · 用记忆里的版本号回答，未核对当前文件
- 日期：2026-11-20
- 标签：研究/工具
- 触发：版本｜依赖｜配置项｜升级
- 事件：我按印象说"这个库 3.x 支持"，实际包里的版本是 2.4。
- 规则：涉及版本号、路径、配置项名称时，先读实际文件或跑一次查询命令，再回答。
- 校验：答案里出现具体版本号或路径，但本轮没有任何读取或查询动作 → 违规
- 失效：0
- 状态：active
```

### 例 3｜边界：不该写的

用户说「你回答得太长了」，但只出现这一次，没有别的线索。

- 可以写：`沟通` 类规则「用户说"太长"之后，同一话题下正文 ≤ 5 行」
- **不要**写「用户不喜欢长回答」——这是偏好推断，不可检验，而且会污染检索

## 写完之后

1. 更新索引区那一行（含触发词与失效次数）。
2. 正文追加在索引区之后、**最新在前**，索引同样最新在前——两处顺序必须一致。
3. 一致性检查：顶部索引的行数 == 正文里 `状态：active` 的条目数。不等就按正文重建索引。
